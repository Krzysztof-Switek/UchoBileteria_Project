## Rozstrzygnięte „open decisions" ze spec (sekcja 27 zaktualizowana)

- Rezerwacja pojemności **atomowo przy utworzeniu zamówienia**; nieopłacone zamówienie wygasa po **20 min** i zwalnia miejsca.
- Limit 1–10 biletów na zamówienie (konfigurowalny per event).
- Bilet jako HTML e-mail z QR (PDF poza MVP); bez weryfikacji e-maila przed zakupem.
- Zwroty: tylko pełne (zamówienie), tylko przez admina; masowy zwrot przy odwołaniu imprezy.
- Lista awaryjna: na żądanie + automatyczny snapshot CSV 2 h przed imprezą.
- Statusy pul/eventu liczone dynamicznie przy odczycie (bez schedulera); cron tylko do wygaszania zamówień, retry e-maili, snapshotów i kalendarza.
- Twardym limitem jest zawsze `capacity_total` eventu (suma pul może go przekraczać).
- Strefa Europe/Warsaw, waluta PLN (w demo: `DEMO`), rate-limiting zakupu, RODO (retencja e-maili), Google Calendar nieblokująco.
- Do spec dodano sekcję **31. Demo payment mode**.

## Architektura trybu demo (najważniejsze)

- `PaymentProvider` (interfejs): `start_checkout`, `refund`; implementacje `DemoProvider` i `StripeProvider`.
- Webhooki demo podpisane HMAC przechodzą przez **ten sam** potok co Stripe: weryfikacja podpisu → `payment_events` → idempotencja → przejścia statusów → wydanie biletów.
- Przełącznik `PaymentConfig` (singleton, panel admina): DEMO ↔ LIVE; przejście na LIVE odmawia działania bez `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET` i jest logowane w audycie.
- Zwrot zamówienia demo nigdy nie woła Stripe (provider zapisany na zamówieniu).

### Zmiana: e-maile w czasie rzeczywistym (commit `befa0c3`)

Na życzenie: system ma działać jak żywy — **bez ręcznego kolejkowania**.
Przebudowano wysyłkę: e-mail (bilety, zwrot) wychodzi **natychmiast po
zatwierdzeniu transakcji płatności** (`transaction.on_commit` → `send_now`).
Wiersz w outboxie zostaje wyłącznie jako zabezpieczenie — cron `send_emails`
ponawia tylko po awarii SMTP (do 5 prób). Dodano 2 testy (natychmiastowa
wysyłka + awaria SMTP → retry przez cron); razem **184 testy zielone**.

Zweryfikowano na działającym serwerze prawdziwym zakupem przez HTTP
(GET strona → POST zakup → POST zapłata w kasie demo): e-mail
„Twoje bilety: Testowy koncert UCHO" → switek.k@gmail.com wyszedł
automatycznie w momencie płatności (w dev do konsoli serwera — backend
konsolowy).

Jedyny nie-„żywy" element w dev to adresat e-maili: bez `EMAIL_URL` Django
drukuje wiadomości do konsoli. Aby dostawać prawdziwe maile:
```
EMAIL_URL=smtp+tls://switek.k%40gmail.com:HASLO_APLIKACJI@smtp.gmail.com:587
DEFAULT_FROM_EMAIL=switek.k@gmail.com
```
(albo Mailpit lokalnie: `EMAIL_URL=smtp://localhost:1025`, podgląd na :8025).

### Przepis na pełny przeklik cyklu demo

1. `/wydarzenia/test-koncert/` → e-mail + ilość → **Kup bilet**.
2. Kasa demo: **Zapłać** (albo: odrzuć / opóźniony webhook / porzuć) →
   strona zamówienia z QR, e-mail wysłany automatycznie.
3. `/wejscie/` → skaner lub szukaj → **Wpuść** (zielony ekran);
   drugi skan tego samego biletu → czerwony „już wykorzystany".
4. **Lista awaryjna (CSV)** — przycisk na stronie wyboru wydarzenia.
5. Zwrot: admin → *Zamówienia* → akcja „Zwróć zaznaczone" → e-mail o zwrocie
   sam wychodzi, bilet przestaje wpuszczać, miejsca wracają do puli.
6. `/raporty/` — wpłaty/zwroty/saldo w DEMO na bieżąco; *Zdarzenia płatności*
   i *Wpisy audytu* w adminie pokazują każdy krok.
7. Dodatkowo: konto DOOR_STAFF (bez `is_staff`) widzi tylko skaner;
   próba włączenia trybu LIVE bez kluczy Stripe jest odrzucana.
